# ProofPass의 문제 범위와 기존 기술 비교

검토일: 2026-09-21. 공식 공개 자료와 현재 구현을 비교한 문서이며, 경쟁 제품을 직접 실행한 성능·보안 평가나 시장 전체의 신규성 조사는 아니다.

## 1. 문제와 현재 기여

메인 메시지: **Prove permission privately. Enforce it at execution.**

ProofPass privately proves that a payment request satisfies identity, credential, delegation and limit conditions, then re-checks revocable state before the destination program executes the payment.

발표의 중심은 **Private policy → Authorization → Actual payment → Revocation → Old authorization rejected**다. 0.05 SOL 지급과 별도 미사용 승인 차단을 함께 보여준다. 취소 적용은 trusted observer가 목적지 상태에 반영한 이후이며, 이미 지급된 자금을 되돌리지 않는다. 아래 2026-09-21 비교 검토의 범위와 근거는 유지한다.

**외부 자격을 근거로 지급을 승인한 뒤 그 자격이 회수됐다면, 다른 체인의 지급 프로그램에서도 미사용 승인을 거절하도록 연결해야 한다.** 원본 신원정보와 전체 위임 한도를 공개하지 않고 이 흐름을 구현하고 검증하는 것이 현재 ProofPass의 범위다.

에이전트는 이 경로의 실행 주체다. 에이전트의 추론 품질, 구매 판단, 프롬프트 인젝션 탐지, 신용 평가를 구현하지 않는다. 데모에서 에이전트 역할의 키로 요청·서명하는 것과 자율 AI 구매 제품을 제공하는 것은 구별한다.

제공하는 것은 OpenDID SDK 검증, XRPL 자격 관측, Midnight 정책 증명, Solana 지급을 잇는 참조 구현과 실행 증거다. 이 조합의 구현 사실은 검증할 수 있지만, 조합이 다르다는 사실만으로 고객 가치나 기술적 독창성이 입증되지는 않는다.

## 2. 이미 존재하는 기능

| 공식 자료 | 확인한 범위 | 설명에 반영할 점 |
|---|---|---|
| [T54 Trustline 개요](https://docs.t54.ai/docs/trustline/overview), [위험 엔진](https://www.t54.ai/docs/trustline/risk-engine) | 지급 전 정책·위임·거래 맥락·외부 신호를 평가하고 판단 근거를 기록한다. | “에이전트가 지금 지급해도 되는가”는 공통 문제다. T54가 외부 자격을 다루지 못한다고 주장하지 않는다. |
| [AP2 권한 프레임워크](https://ap2-protocol.org/ap2/agent_authorization/) | 사용자·에이전트 권한과 지급 위임을 다룬다. | 위임과 거래 조건은 기존 프로토콜의 영역이다. ProofPass의 자체 스키마는 AP2 지원이 아니다. |
| [Verifiable Intent 명세](https://www.verifiableintent.dev/spec/) | 신원·사용자 위임·에이전트 실행의 암호학적 연결과 선택적 공개를 정의한다. 검토한 페이지는 초안으로 표시돼 있다. | “기존 위임은 모두 공개된다”는 비교는 부정확하다. 선택적 공개와 비공개 조건 계산의 차이를 실제 요구별로 비교해야 한다. |
| [Privado ID 크로스체인 검증](https://docs.privado.id/docs/verifier/on-chain-verification/cross-chain/), [온체인 검증](https://docs.privado.id/docs/verifier/on-chain-verification/overview/) | ZK 자격 검증과 다른 체인의 사용자·발급자 상태를 가져오는 흐름을 설명한다. 크로스체인 안내에는 신뢰하는 상태 서명 서비스도 명시돼 있다. | 비공개 자격, 다른 체인의 상태, 온체인 조건부 실행을 독자적인 발명으로 소개하지 않는다. |
| [XRPL Credentials](https://xrpl.org/docs/concepts/decentralized-storage/credentials), [Permissioned Domains](https://xrpl.org/docs/concepts/tokens/decentralized-exchange/permissioned-domains) | 자격 수명주기와 자격 기반 접근 제어를 제공한다. | 자격 회수와 접근 제어 자체는 기존 기능이다. ProofPass는 이를 사용하는 특정 외부 지급 경로를 검증한다. |

자료에 특정 기능이 명시되지 않았다는 것은 그 기능이 없다는 증거가 아니다. 제품, 초안 프로토콜, 구현 가이드를 같은 성숙도의 완제품으로 취급하지 않는다. 위 비교만으로 어느 제품보다 우수하거나 동일 조합이 세계 최초라고 결론 내릴 수 없다.

## 3. 구현과 설명의 일치 여부

| 설명할 수 있는 것 | 근거와 경계 |
|---|---|
| 자격 삭제 반영 후 기존 승인으로 지급 거절 | [실행 기록](../evidence/preprod/live-flow.json). 승인 만료 전에 검사했지만, 삭제와 목적지 반영 사이에는 지연이 있다. |
| 실행 시 자격·위임 상태 재검사 | [Solana 프로그램](../solana/programs/authorization/src/lib.rs)의 `execute_payment`와 `validate_request`. 관측자가 등록한 상태를 검사하며 XRPL 합의를 직접 검증하지 않는다. |
| 비공개 거래당 한도 검사 | [Midnight 회로](../midnight/contract/src/policy.compact)의 요청 금액과 위임 한도 비교. 누적 지출 한도나 여러 체인의 공통 예산은 구현하지 않았다. |
| 신원과 외부 근거의 연결 | 신뢰하는 어댑터가 검증한 근거에 서명하고 회로가 이를 검사한다. 원본 OpenDID 증명 전체의 재귀 검증을 주장하지 않는다. |
| 일회용 승인과 프로그램 지급 제어 | 승인 소비와 요청 바인딩을 검사한다. 해당 프로그램의 vault 지급 경로가 범위이며 사용자의 모든 지갑 송금을 통제하지 않는다. |
| 공개 체인에 원본 신원·전체 위임 한도를 올리지 않음 | 로컬 어댑터와 prover는 비공개 입력을 처리한다. 실제 지급 주소·금액·시각이 모두 비공개라는 뜻은 아니다. |
| 목적지에 승인 등록 | 신뢰하는 relay가 등록한다. Solana가 Midnight ZK proof를 직접 검증하는 trustless bridge가 아니다. |

기존 README의 넓은 “에이전트 지급 통제” 설명을 위 연동 문제로 좁혔다. 기존 기획서는 설계 당시 기록으로 남기고 이번 검토로 연결한다. 운영 화면은 단계별 실행 결과를 보여주는 데모이며, 기존 실행 영수증과 영상은 새 제품 주장에 맞춰 변경하지 않는다.

## 4. 제품으로 발전시킬지 판단하는 기준

아래는 아직 수행하지 않은 검증이다. 동일한 요구와 같은 신뢰 수준으로 비교해야 한다.

1. **실제 수요:** 자격을 회수한 뒤 다른 지급 시스템의 미사용 승인도 막아야 하는 운영 사례가 있는가? 기존 연동에서 무엇이 부족하며, XRPL 자격을 실제로 사용하는가?
2. **기존 방식과 비교:** 중앙 승인 API, 기존 VC 검증기, T54·AP2·VI 기반 구성으로 같은 정상 지급·자격 삭제·위임 취소·재사용·관측 중단 시나리오를 구현할 수 있는가?
3. **비공개 검증의 필요:** 누가 어떤 입력을 보지 않아야 하는가? 선택적 공개만으로 충분한가, 숨긴 값에 대한 조건 계산이 필요한가? 현재 운영자·prover가 입력을 보는 모델을 고객이 수용하는가?
4. **운영 비용과 실패:** 연동 작업량, 증명·등록 비용, 지갑 준비, 상태 반영 지연, 정상 거래의 만료 실패, 장애 복구 부담을 비교한다. 현재 한 번의 실행 시간은 경쟁 우위의 근거가 아니다.
5. **확장 결정:** 기존 방식이 요구를 충족하면 이를 채택하거나 연결하는 편이 타당하다. 반복적으로 남는 요구가 확인될 때 해당 부분을 모듈로 발전시킨다. T54나 AP2에 대한 연결은 현재 가능한 방향일 뿐 구현된 통합이 아니다.

### 고객 확인에 사용할 질문

다음 질문은 인터뷰 준비용이다. 실제 인터뷰나 고객 접촉을 수행한 기록은 아니다.

- 현재 어떤 신원·회원 자격 시스템을 운영하며, OpenDID를 실제로 사용하는가?
- 어느 온체인 서비스와 연결하려고 하며, 최근 연결이 필요했던 업무는 무엇인가?
- 자격 회수 전에 발급된 미사용 승인은 어떤 시점부터 막혀야 하는가? 허용 가능한 반영 지연은 얼마인가?
- 현재 API·VC 검증·지급 계약으로 처리할 때 구체적으로 무엇이 부족한가?
- 원본 신원이나 위임 한도를 누구에게 숨겨야 하며, 로컬 운영자와 prover가 입력을 처리하는 구조는 수용 가능한가?
- 이미 지출하는 연동·운영 비용은 무엇이며, 유료 실증에 참여할 담당자와 예산이 있는가?

답변은 실제 사례, 현재 해결 방식, 부족한 점, 공통 요구, 유료 실증 의사로 기록한다. 여러 팀에서 반복되는 요구가 확인되면 공통 SDK·운영 서비스 가능성을 평가하고, 요구가 대부분 개별적이면 맞춤 구축으로 판단한다. 수요가 확인되지 않으면 해커톤 기술 실증으로 마무리할 수 있다. 이는 선택 기준이며 현재 외주 수요나 제품 시장이 확인됐다는 뜻은 아니다.

OpenDID 사용은 특정 기존 시스템과의 연동 출발점이다. 한국 기반 기술이라는 점만으로 우위나 국내 도입을 주장하지 않으며, 현재 테스트 발급자 검증을 정부 모바일 신분증·공공 신원 체계 연동으로 표현하지 않는다.

## 5. 발표와 문서에 사용할 표현

> ProofPass는 외부 자격의 변경을 다른 체인의 위임 지급에 반영하는 해커톤용 참조 구현입니다. 기존 신원·자격 기술과 비공개 정책 증명을 연결하고, 정상 지급뿐 아니라 자격 삭제 후 미사용 승인 거절까지 테스트넷 기록으로 보여줍니다. 이후 제품화 여부는 실제 연동 수요와 기존 방식 대비 이점을 확인해 판단합니다.

“최초의 에이전트 신뢰 계층”, “기존 서비스는 자격·취소·프라이버시를 처리하지 못한다”, “체인이 바뀌면 반드시 KYC를 다시 해야 한다”, “완전 무신뢰·즉시 취소·모든 지갑 지급 통제”는 주장하지 않는다. 코드와 실행 증거가 보여주는 범위, 제품 가설, 미검증 비교를 구분한다.
