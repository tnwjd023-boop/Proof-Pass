# 기업에서 Agent까지 이어지는 권한 — 설계 초안

상태: 방향 합의 후 작성한 설계. 아래 기업 권한 기능은 아직 구현·배포하지 않았다. 기존 테스트넷 영수증은 개인 위임 경로의 증거이며 이 설계의 검증 결과가 아니다.

## 목적과 문제

비전: **법인의 경계가 AI Agent까지 확장된다.**

제품 가설: 기업이 부여한 업무 권한을 Agent까지 연결하고, 외부 서비스가 그 연결과 현재 유효성을 검증해 행동을 허용하도록 한다. 기술적으로 검증하는 것은 신뢰하는 발급자가 확인한 조직 근거, 조직 키의 권한 부여, 담당자의 재위임, 구체적인 요청의 조건 충족이다. 법적 대리권이나 거래의 법적 효력을 자동으로 보증하는 서비스로 소개하지 않는다.

첫 대상 가설은 외부 서비스에 Agent 구매를 맡기려는 기업과, 그 Agent의 권한을 확인해야 하는 서비스 제공자다. 실제 고객 수요는 아직 확인하지 않았다.

핵심 질문: **담당자의 구매 권한이 회수됐을 때, 그 담당자가 Agent에 발급한 미사용 승인도 지급처에서 거절되는가?**

## 접근 비교와 선택

| 접근 | 장점 | 한계 |
|---|---|---|
| 기존 개인 위임에 회사 표시만 추가 | 빠른 화면 시연 | 위임자의 권한과 재위임을 검증하지 못함 |
| 고정된 조직 → 담당자 → Agent 구조 구현 | 권한 축소와 상위 권한 회수 효과를 직접 검증 가능 | 회로·상태·지급 계약의 변경 필요 |
| 범용 조직 권한 플랫폼 | 임의 깊이 재위임·조직 정책까지 확장 가능 | 현재 고객 검증과 해커톤 범위를 넘음 |

**고정된 2단계 위임 구조를 선택한다.** 첫 실행 검증은 테스트 SOL을 사용한다. 사용자가 제안한 $10 한도·$5 API 구매는 후속 제품 시나리오이며, 달러 결제나 API 제공이 구현되기 전에는 실행 결과로 표시하지 않는다.

## 첫 검증 범위

- 합성 조직 A, 조직 관리 키, 담당자 키, Agent 키, 지정된 서비스 수취인 각 하나.
- 조직이 담당자에게 `API_PURCHASE` 범위, 거래당 최대 0.10 test SOL, 유효기간과 재위임 허용을 부여한다.
- 담당자는 동일한 범위 또는 더 좁은 조건으로 Agent에 위임한다. Agent는 다시 위임할 수 없다.
- 0.05 test SOL 지급을 승인하고 0.15 test SOL, 다른 업무 범위, 상위 권한 회수 후 지급을 거절한다.
- 이 단계의 `API_PURCHASE`는 지정된 데모 실행 경로의 정책 식별자다. 실제 외부 API 구매·상품 적합성·서비스 전달을 증명하지 않는다.
- 공개망 변경은 로컬 검증 통과 후 별도 정책 버전과 배포로 수행한다. 기존 배포와 실행 증거를 보존한다.

## 권한 데이터와 검증 규칙

모든 서명·해시는 버전과 용도를 구분하고, 네트워크·정책·목적지 프로그램을 포함한 정규 인코딩에 결합한다. 표시용 회사명이나 이메일을 권한 식별자로 사용하지 않는다.

| 객체 | 필수 내용 |
|---|---|
| OrganizationCredential | 조직 ID, 신뢰 발급자 ID, 조직 관리 키, 자격 참조·버전, 유효기간 |
| OfficerGrant | 조직 ID, 자격 참조, 담당자 키, grant ID·버전, 업무 범위, 자산, 목적지·수취인, 거래당 한도, 기간, 재위임 허용, 조직 서명 |
| AgentDelegation | 상위 grant 해시·버전, 조직 ID, Agent 키, delegation ID·버전, 업무 범위, 자산, 목적지·수취인, 거래당 한도, 기간, 담당자 서명 |
| ActionRequest | 조직·grant·delegation 참조, Agent 키, 업무 범위, 자산·금액, 수취인, vault, 목적지 프로그램·네트워크, 요청 ID, 만료 |
| AuthorityStatus | 각 권한 참조의 활성 여부, 단조 증가 버전, 관측 또는 갱신 시각, 유효기간 |

자식 권한의 기간은 부모 기간 안에 있어야 하며 거래당 한도는 부모 이하로 제한한다. 첫 버전은 단일 업무 범위·자산·수취인·목적지의 정확 일치를 사용하고 와일드카드를 지원하지 않는다. 조직 ID와 부모 참조는 전체 연결에서 일치해야 한다. 담당자 교체·재발급은 새 버전을 사용하며 과거 자식 위임이 자동으로 되살아나지 않는다.

Agent 키가 요청에 서명해야 한다. 요청 해시에는 업무 범위와 전체 권한 참조가 포함돼야 하며, 목적지 프로그램은 지원하는 업무 경로와 요청을 대조한다. 구매가 아닌 호출에 `API_PURCHASE` 문자열을 붙이는 것만으로 권한이 생겨서는 안 된다.

한도는 거래당 한도다. 여러 요청의 누적 예산, 다중 자산 환율, 임의 깊이 재위임, 다중 관리자 승인은 이번 범위에 넣지 않는다.

## 구성요소별 역할

1. **OpenDID·조직 근거 어댑터:** 기존 사람 신원 검증을 재사용한다. 별도의 테스트 조직 자격과 조직 관리 키를 연결한다. 사람의 신원 증명만으로 회사의 담당자 권한이 생기지 않는다. 실제 법인 발급자·등기·KYB 연동은 별도 범위다.
2. **XRPL 관측자:** 조직 자격의 발급·수락·삭제 상태를 기존 관측 방식으로 전달한다. 첫 버전의 담당자·Agent 위임 상태는 Solana에서 관리하며, XRPL에 범용 delegation 기능이 구현됐다고 표현하지 않는다.
3. **Midnight 정책:** 서명된 근거와 부모·자식 권한의 연결, 조건 축소, 요청 바인딩을 검증한다. 비공개 한도를 공개하지 않고 요청이 범위 안임을 증명한다. 원본 신원 증명과 XRPL 합의를 직접 검증한다는 뜻은 아니다.
4. **Relay:** 확정된 정책 승인을 정확한 요청과 권한 버전에 매핑해 목적지에 등록한다. 기존 신뢰 가정을 유지한다.
5. **Solana 지급 프로그램:** 조직 키가 담당자 grant를 등록·취소하고 담당자가 자식 delegation을 등록·취소하도록 서명 권한을 검사한다. 등록한 권한 commitment와 증명의 권한을 일치시킨다. 지급 직전에 조직 자격·상위 grant·자식 delegation의 활성 상태와 버전·만료, Agent 서명, 요청 해시, 승인 소비 여부를 다시 확인한다.

첫 조직 vault는 조직 관리 키에 묶고 권한 등록이나 입출금 권한이 담당자에게 암묵적으로 넘어가지 않게 한다. 기존 개인 vault를 회사 자산으로 이름만 바꾸거나 기존 자금을 옮기지 않는다.

## 상위 권한 회수

조직 관리 키가 담당자 grant를 취소하면 해당 상태의 버전을 올리고 비활성화한다. 지급은 항상 현재 부모 상태를 조회하므로 모든 자식 위임을 열거해 취소하지 않아도 이전 부모 버전의 미사용 승인을 거절해야 한다.

조직 자격이 XRPL에서 삭제되는 경우에는 기존과 같이 관측·목적지 반영 지연이 있다. 즉시 크로스체인 취소를 주장하지 않는다. 유효기간이 지난 관측 근거로는 중단한다. 이미 확정된 지급을 소급해서 되돌리는 구조는 아니다.

승인 생성과 실행 사이에 담당자 권한이 회수되는 경우를 핵심 경쟁 상태로 검증한다. 승인 생성 때만 부모를 검사하는 구현은 불충분하다.

## 재사용과 변경

| 재사용 후보 | 필요한 변경 |
|---|---|
| OpenDID 세션·지갑 바인딩, 테스트 발급 도구 | 조직 자격·관리 키·담당자 역할의 별도 연결 |
| XRPL 상태 관측과 신선도 검사 | 조직 자격의 의미와 조직 ID 결합 |
| Midnight 서명 검증·한도·요청 commitment | 부모·자식 grant 및 업무 범위, 새 정책·인코딩 버전 |
| Solana vault·일회용 승인·위임 취소 | 조직 vault와 부모 grant 상태, 지급 시 상위 권한 재검사 |
| 실행 영수증·재개·데모 화면 | 별도 기업 권한 실행 기록, 거절 원인 및 구현 상태 표시 |

## 수용 기준

| 사례 | 기대 결과 |
|---|---|
| 유효한 조직·담당자·Agent, 0.05 test SOL | 지정 vault에서 정확히 한 번 지급 |
| 0.10 한도에서 0.15 요청 | 승인 거절, 잔액 변화 없음 |
| 부모보다 큰 자식 한도·긴 기간·다른 scope | 승인 거절 |
| 위임 권한 없는 담당자, 다른 회사 grant, 잘못된 서명 | 거절 |
| 미사용 승인 발급 후 담당자 grant 취소 | 승인 만료 전에도 지급 거절 |
| 자식 위임만 취소 | 그 자식의 지급 거절 |
| 담당자 grant 재발급 | 과거 승인·자식 위임은 계속 거절 |
| 조직 자격 삭제가 목적지에 반영됨 | 지급 거절 |
| 만료·오래된 상태·잘못된 수취인·목적지·Agent | 지급 거절 |
| 요청 재사용 및 완료 실행 재개 | 추가 지급 0 |

거절은 API 응답뿐 아니라 지급 전후 잔액과 온체인 상태로 확인한다. 회로의 권한 축소 검사와 Solana의 실행 시점 상위 상태 검사를 각각 시험한다. 기존 개인 위임 테스트도 유지해 회귀를 확인한다.

## 제품 주장과 남은 검증

기업 권한 연결은 제품 가설이다. 기존 T54·AP2·Verifiable Intent 등의 위임·정책 기능과 겹친다. 비교 근거는 [기존 기술 검토](../../POSITIONING.md)에 보존한다. DFlow Proof와 신원·권한의 역할을 구분할 수 있지만 그 구분만으로 전체 시장의 차별성이 입증되지는 않는다.

다음 고객 검증은 기업 담당자가 외부 Agent에 권한을 부여하는 실제 업무, 상위 권한 회수 요구, 기존 IAM·승인 API·위임 규격의 부족한 점에 집중한다. 범용 기업 권한 제품이나 OpenDID 기반 국내 실고객 도입을 이미 확보한 것으로 소개하지 않는다.
